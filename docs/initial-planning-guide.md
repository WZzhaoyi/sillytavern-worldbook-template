# 初始策划指南：把设定写成可持续运行的叙事系统

本指南用于 Step 0。目标不是预写一条必须照走的主线，而是先定义：什么永远成立、什么可以变化、变化由什么触发、变化后保存在哪里。完成后输出 `literature/策划蓝图.md`，再据此配置世界书、场景和 MVU 状态模型。

## 1. 参考架构的安排

大型开放世界角色卡通常不是单一“剧情库”，而是以下模块共同运行：

| 模块 | 保存什么 | 何时参与 | 谁生成内容 |
|---|---|---|---|
| 世界规则 | 力量边界、资源代价、时间尺度、社会常识 | 常驻或高优先级 | 作者预设 |
| 内容层 | 不同地域、时代、阶段才适用的规则与资料 | 满足解锁条件后 | 作者预设，运行时选择 |
| 实体资料 | 已命名的人物、地点、势力、物品 | 关键词命中或场景需要时 | 作者预设 |
| 生成规则 | NPC、地点、任务、机遇、遭遇的组合约束 | 缺少现成实体或需要新内容时 | LLM 当场生成 |
| 事件调度 | 活跃事件、阶段、冷却、下一步后果 | 时间或因果推进时 | LLM 在状态约束下推进 |
| MVU 状态 | 当前时间、地点、人物关系、物品归属、事件阶段 | 每轮读取，发生变化时写回 | 开局快照 + LLM 增量更新 |

这意味着：固定的是“法则、已知事实和生成边界”，不是每一次遭遇的正文。LLM 可以当场创作世界动向，但必须受当前状态、地理、人物动机、力量差距和事件阶段约束。

### 1.1 情节推进不是固定主线

参考架构采用的是“多条事件线 + 阶段推进”，而不是章节号驱动：

1. 世界中只维持少量活跃大事件，避免事件无限堆积。
2. 每个事件按“出现端倪 → 矛盾升级 → 局势转折 → 结果落地”推进。
3. 主角未介入时，事件仍可在远处发展；主角介入后，结果必须吸收其行动造成的影响。
4. 已结束事件的永久后果先落实到世界或实体字段，随后退出活跃集合；需要时再产生新的事件线。
5. 动态遭遇受冷却、场景私密性、地理距离和角色能力限制，不能为了热闹而空降人物。

“起承转合”只是默认四阶段表示法。作品可以替换为“线索/调查/对抗/结案”“平静/升温/破裂/余波”等更贴合题材的名称。

### 1.2 设定不是全部常驻

参考架构将设定分成三种注入方式：

- 常驻核心：只放缺失后会让世界失去基本逻辑的规则。
- 条件内容包：按地域、时代、阵营或成长阶段启用，未到达时不注入。
- 关键词资料：具体人物、地点、势力和物品，仅在正文命中或场景需要时注入。

这种分层比“把全部设定塞进 system prompt”更可靠：上下文更小，互相冲突的规则更少，也不容易让 LLM 提前泄露未解锁内容。

### 1.3 生成器生成的是受约束实例

NPC、地点、势力、任务或遗迹生成规则应先给出组合轴，再让 LLM 填充实例。例如 NPC 至少受以下因素约束：

- 身份及其可获得的资源；
- 相对主角的能力区间；
- 当前地点与到场原因；
- 性格、短期目标和现有关系；
- 能力、装备与身份的一致性；
- 此次行动的风险、收益和可观察后果。

程序化生成不是“无中生有”。它的可靠性来自约束之间能够互相校验。

### 1.4 开局创建器只负责会话实例

开局创建器的输入可以包含主角身份、能力、关系、初始地点、难度和内容偏好。提交后应完成两件事：

1. 形成给 LLM 的开局条件，用于生成第一段正文。
2. 一次性写入世界、人物、物品、地点、事件的完整 MVU 快照。

不要为每次开局动态创建常驻世界书条目。多次开局会使旧人物或旧能力继续注入，形成冲突。作品的静态规则属于世界书；本次开局独有的主角、同伴、能力和出生点属于 MVU 状态。

### 1.5 连续性检查只检查可观察结果

正文前检查应回答：本轮有哪些事实约束叙事？不要求模型公开冗长思维过程。一个紧凑的 `StateCheck` 足以覆盖：

- 时间、地点和移动是否可达；
- 哪些人物在场，各自知道什么、想做什么；
- 哪些物品实际可用；
- 哪些事件正在推进；
- 力量、资源、关系和人物认知边界；
- 本轮最自然的叙事焦点。

正文后只更新已经发生的事实。展示性栏目、远处人物和未变化实体不应被强制改写；更新频率应与变量的实际波动频率一致。

## 2. Step 0 策划顺序

按以下顺序策划，前一项会限制后一项。不要先堆人物百科，再反过来寻找玩法。

### 2.1 体验承诺

先用三句话说明：

- 玩家在故事中是谁，可以做什么；
- 世界会以什么方式抵抗或回应玩家；
- 一次典型的 10 轮对话应产生什么体验。

同时写明题材、基调、叙事视角、内容边界和失败是否允许。它们是后续取舍的判据。

### 2.2 不变量

列出 3～7 条不可被普通剧情推翻的世界规则。每条必须能回答：

- 规则约束谁；
- 触发条件是什么；
- 代价或后果是什么；
- 是否存在例外，例外由谁承担更高代价。

只把真正不可缺少的规则设为常驻。氛围描述、人物百科和具体剧情不属于不变量。

### 2.3 核心循环与成长

用一个闭环描述玩法：

`行动 → 消耗或风险 → 世界反馈 → 状态变化 → 新选择`

需要数值化的资源应同时设计来源、消耗、恢复、上下限和归零后果。成长必须带来新的选择或新的风险；如果一个数值只用于面板展示，不影响叙事，就不应进入 MVU。

### 2.4 内容层与解锁门

按地域、时代、阵营或成长阶段划分内容层。每层写明：

- 进入条件与退出条件；
- 本层新增的规则、势力和风险；
- 哪些旧规则继续生效，哪些被替换；
- 如何防止未解锁资料提前进入上下文。

模板本身不预设“下界/上界”等具体层级。只有作品确实存在分层时才使用这一机制。

当前模板采用构建时单选：公共规则放在 `setting.source_files`，互斥层分别放在 `setting.layers`，只把 `active_layer` 指向的层写入世界书。切换层后重新生成并导入世界书。这样没有自动热切换，但能保证两个相反内容包不会同时进入提示词。

### 2.5 状态所有权

每个事实只能有一个权威路径。优先使用以下分工：

| 事实 | 权威位置 |
|---|---|
| 当前时间、当前场景、当前地点 | `世界` |
| 人物位置、状态、目标、关系、数值 | `人物/<名称>` |
| 物品归属、数量、状态 | `物品/<名称>` |
| 地点自身是否发现、受损或封锁 | `地点/<名称>` |
| 跨回合冲突、目标、阶段和结果 | `事件/<名称>` |

不要在地点里再保存一份人物列表，也不要在人物和物品里各保存一份物品所有权。

### 2.6 事件调度

决定作品是否需要后台世界动向。需要时，为事件定义：

- `状态`：未触发、进行中、已完成、已失败或已搁置；
- `阶段`：作品自己的 3～5 个阶段；
- `触发条件`：玩家行动、时间、地点、关系或资源阈值；
- `推进条件`：什么事实发生后才能进入下一阶段；
- `影响范围`：远处传闻、局部事件或直接危机；
- `收束结果`：结束后改变哪些世界事实；
- `并发上限`：通常 1～3 条活跃主事件已经足够。

不要规定“每轮必须新建或推进事件”。只有时间或因果确实前进时才更新，否则世界会显得机械且浪费 token。

### 2.7 程序化生成器

只为需要反复出现、无法全部预写的内容设计生成器。每种生成器至少填写：

| 项目 | 说明 |
|---|---|
| 输入 | 当前地点、阶段、角色能力、已知事实等 |
| 组合轴 | 身份、目的、资源、危险、规模等 |
| 硬约束 | 不能违反的地理、能力、知识和因果规则 |
| 输出 | 要创建的实体及其完整字段 |
| 持久化 | 哪些结果写入 MVU，哪些只是一次性描写 |
| 去重 | 如何避免与现有实体重名或功能重复 |
| 失效 | 何时移除、归档或停止继续展开 |

优先设计一个约束完整的生成器，而不是五个只有形容词列表的生成器。

### 2.8 人物自治与关系

人物不能只在被玩家看见时存在。为重要人物写明：

- 长期诉求与当前目标；
- 可接受的代价和不可跨越的底线；
- 对玩家的关系阶段以及阶段变化证据；
- 离场期间可能进行的行动；
- 能力成长是否需要与玩家相同的资源和风险。

关系数值变化必须由可观察事件支持，并允许逆转。不能只因一轮礼貌对话就跨越多个关系阶段。

### 2.9 开局集合

每个预设开局都应是完整状态快照，而不是给同一份初始状态打补丁。至少确定：

- 时间、地点和场景；
- 在场人物及其当前目标；
- 已知物品与所有权；
- 已发现地点；
- 正在发生的事件及其当前阶段；
- 面向玩家的第一个可回应钩子。

自定义开局也遵守同一 Schema。表单只收集会改变开局的字段；纯装饰字段留给正文描写。

### 2.10 更新预算

按波动频率划分变量：

- 高频：当前场景、在场人物、即时资源；发生变化时更新。
- 中频：关系、事件阶段、物品状态；有明确证据时更新。
- 低频：地点永久变化、势力格局、长期成长；重大事件后更新。
- 非状态：榜单文案、气氛短句、随机闲谈；不要仅为面板而每轮保存。

最终检查：若删掉某字段不会影响后续叙事选择或一致性，就不要追踪它。

## 4. 冲突消解与条目注入边界

同一类指令只允许一个权威来源：

| 内容 | 唯一来源 | 其他位置不得重复 |
|---|---|---|
| 叙事者身份、作品范围、叙事原则 | `narrator.persona` | 世界书设定、阶段文件 |
| 具体文风执行规则 | `style_instructions` | persona、MVU 协议 |
| 固定叙事视角 | `style_instructions` | persona、MVU 状态、世界书模式条目 |
| 数值边界与阶段顺序 | `state_model.character_metrics` | 角色 `_stages` 文件 |
| 角色阶段行为 | 对应角色 `_stages` 文件 | 世界书总设定、运行时状态 |
| 事件推进位置 | `事件/<名称>/阶段` | 百分比进度、每轮剧情摘要 |
| 当前人物、物品、地点、事件事实 | MVU 五集合 | 动态创建的常驻世界书 |

生成后的系统常驻条目应只有：MVU 生命周期协议和当前变量；另外只允许极少量带 `★` 的世界公理。具体人物、地点、势力和物品依靠关键词触发；关系条目同时要求主关键词与至少一个可选过滤键。`[initvar]` 只供 MVU 初始化读取，保持禁用。

互斥内容层不得同时标记为常驻。使用 `setting.active_layer` 只构建当前层；不要用两组相反的常驻提示词要求 LLM 自行判断。

## 5. 从蓝图映射到项目文件

| 蓝图内容 | 项目落点 |
|---|---|
| 世界不变量、内容层规则 | `literature/fanfic/*.txt` 世界书条目 |
| 人物事实与关系阶段表现 | `literature/characters/` |
| 关系网络 | `literature/fanfic/关系网.txt` |
| 固定叙事视角 | `AGENTS.md` 的 `narrator.style_instructions` |
| 状态字段与数值 | `AGENTS.md` 的 `state_model` |
| 预设开局完整快照 | `literature/scenarios/*.md` |
| 开局创建、前检、更新、面板 | 生成器根据 `state_model` 自动生成 |

静态设定负责约束可能性，MVU 负责记住已经发生的事实，LLM 负责在两者之间创作本轮正文。三者不要保存同一事实的副本。
